# (별도 트랙) 실무자 어시스턴스 SDK — 조사와 설계

> 개발 전 설계 문서. HTS 밑에 붙는 한 겹(`BSP.Context.dll`)으로, 범용 AI 가 우리 업무를
> 이해하도록 **무엇을 읽을지 정해 주는** 층이다.

---

# 1부 · 필요성 — 조사로 확인된 것

## 1-1. 문제는 토큰 값이 아니라 **성능 저하**다

컨텍스트를 많이 넣으면 느려지고 비싸지는 정도가 아니라, **정답률이 떨어진다.**
2026년 기준으로 이것은 추측이 아니라 측정된 현상이다.

| 현상 | 측정값 | 출처 |
|---|---|---|
| **컨텍스트 로트** — 입력이 길수록 정확도 하락 | 프런티어 모델 **18개 전부** 저하. 통제 실험에서 정답률 **0.92 → 0.68** (수백 → 3,000 토큰) | Chroma / TinyFish |
| **중간 실종** — 증거가 가운데 있으면 못 본다 | 문서 20개 중 5~15번 위치에 두면 정확도 **30%+ 하락** (U자 곡선) | Liu et al., Stanford/TACL |
| 긴 맥락 뒤 감시 실패 | 80만 토큰의 평범한 활동 뒤에 나온 위험 행동을 **2~30배** 더 자주 놓침 | 2026-05 논문 |

리빗 모델 하나가 요소 4만 개다. 그대로 넘기면 위 세 현상이 **동시에** 일어난다.
"컨텍스트 창이 크니 다 넣으면 된다" 는 2026년에 이미 반증된 전제다.

## 1-2. 압축은 **손해가 아니라 이득**이다

가장 중요한 조사 결과. 컨텍스트를 줄이면 성능이 깎일 것 같지만, 실제로는 **줄이면서 올랐다.**

| 결과 | 수치 |
|---|---|
| 토큰 사용 | **10~70% 감소** |
| 정확도 | **+4 ~ +4.81%p 상승** |
| 지식 집약 과제 | TriviaQA **+24.5%**, HotpotQA **+29.0%** |

즉 우리가 하려는 일(요소를 주지 말고 판정을 줘라)은 **비용 절감 수단이 아니라 성능 개선 수단**이다.
잡음을 걷어내면 모델이 더 잘한다.

## 1-3. 그렇다면 **모델을 학습시켜야 하나?** — 아니다

| 무엇에 강한가 | 방법 |
|---|---|
| 사실 회상 (무엇이 어디에 있나) | **검색(RAG) 이 파인튜닝보다 낫다** |
| 출력 형식 · 도메인 어휘 · 말투 | 파인튜닝 |

정리하면 **"인터페이스는 튜닝하고, 내용은 검색한다."**
우리가 필요한 것은 사실 회상(이 도면·이 라인·지난번 그 오류)이므로 **검색 쪽**이다.

→ **생성 모델(SLLM)을 학습시킬 이유가 없다.** 문장 생성은 Claude 가 이미 잘한다.
우리가 만들 것은 **무엇을 꺼내 줄지 아는 층**이고, 그것은 규칙 + 임베딩으로 충분하다.

## 1-4. 왜 범용 AI 가 이 자리를 못 채우나

범용 모델은 **무엇이 중요한지 모른다.** 배관 제작도에서
"CWS-101 라인의 스풀 3번이 용접 넘버가 비어 있다" 가 핵심이고 벽·방·시트는 잡음이라는 것을
아는 것은 학습으로 얻는 지식이 아니라 **현장 규칙**이다.

오토데스크가 2027 에 MCP 를 기본 탑재해도(읽기 전용) 이 층은 비어 있다. 채우려면
몇 달 동안 도면에 두들겨 만든 판정 규칙이 있어야 하고, 그것이 우리에게만 있다.

# 2부 · 설계

## 2-1. 경계 — 무엇이고 무엇이 아닌가

```
  [Claude / 범용 AI]        ← 판단하고 문장을 만든다 (우리가 안 함)
          ▲
          │  8KB 스냅샷 + 근거 링크
  ┌───────┴────────────────────────────────┐
  │  BSP.Context.dll   ← 우리가 만드는 것    │
  │   · 압축   업무 어휘로 줄인다            │
  │   · 회상   과거에서 닮은 것을 찾는다      │
  │   · 순위   무엇을 먼저 보일지 정한다      │
  └───────┬────────────────────────────────┘
          │  판정 규칙(NOZ·HTS) · 기록 · 임베딩 인덱스
  [HTS · 런처 · Bridge · MCP]  ← 모델·도면을 실제로 읽는다
```

- **아니다** : 새 MCP 서버 · 생성 모델 · 리빗 API 래퍼 · 오케스트레이션 프레임워크
- **이다** : 그 위에 얹는 얇은 층. SDK 하나, 호출 셋

## 2-2. API — 셋이면 된다

```csharp
public interface IBspContext
{
    // 지금 상태 한 장 (규칙으로 만든 사실 · 8KB 상한)
    Brief Snapshot(Scope scope = Scope.Active);

    // 지금 상황과 닮은 과거를 찾는다 (임베딩)
    IList<Recall> Recall(string situation, int top = 5);

    // 사실 뭉치를 예산 안으로 줄인다 (무엇을 버릴지 아는 것이 핵심)
    Brief Compress(Facts facts, int budgetBytes = 8192);
}
```

```csharp
public sealed class Brief {
    string     Headline;     // "CWS-101 스풀 분할 중, 3번에서 막힘"
    Stage[]    Stages;       // 판정 → 자르기 → 분할 → 제작도, 각 상태
    Fact[]     Facts;        // 라인·스풀·노즐·용접 수치
    Issue[]    Issues;       // 규칙 위반만
    Cursor     More;         // 잘렸으면 이어 보는 손잡이
    Budget     Budget;       // {used, limit, truncated}
}
```

`Budget` 을 항상 실어 보낸다 — AI 가 **스스로 좁혀 물을 수 있게** 하려는 것.

## 2-3. 압축 규칙 — 무엇을 버리나

압축이 이 SDK 의 전부다. 범용 요약기가 못 하는 이유는 **우선순위가 업무 지식**이기 때문이다.

| 남긴다 | 버린다 |
|---|---|
| 규칙 위반 (미태그 · 구배 이탈 · 용접 번호 빔) | 정상인 요소 (전체의 95%) |
| 지금 라인 · 스풀 번호 · 단계 | 잡담 · 중간 시행착오 |
| **사람이 고친 값** (= 정답) | 자동 판정 원문 |
| 반복 실패 (같은 대상 3회 = 첫 답이 틀림) | 성공한 중간 단계 상세 |
| 이상치 (노즐 간격 350 중 1400 인 것) | 분포의 중앙값 근처 |

**"정상은 세고, 이상은 적는다"** 가 한 줄 원칙이다.
정상 3,516개는 `{normal: 3516}` 한 필드, 이상 7개는 각각 한 줄.

## 2-4. 회상 — 임베딩이 필요한 유일한 자리

```
 지금 상황  →  임베딩  →  과거 기록 인덱스에서 코사인 유사도 상위 5
                          "3주 전 같은 증상 · 그때는 끊는거리 24000 으로 풀림"
```

- 모델 : `multilingual-e5-small`(120MB) 또는 `bge-m3`(560MB, 한국어 강함)
- **생성이 아니라 검색이다** — 틀려도 후보가 하나 더 나올 뿐 사고가 안 난다
- 인덱스는 무제한 쌓아도 안전하다 (오염이 안 번진다)
- 반대로 **모델 재학습은 사람이 고친 것만** — 자동 출력을 되먹이면 무너진다

## 2-5. HTS 에 붙는 모양

```
 %APPDATA%\Autodesk\Revit\Addins\<버전>\BSP.Hub\
   BSP.Hub.dll
   BSP.Contracts.dll
   BSP.Context.dll        ← SDK (여기 한 장)
   Tools\                 ← 도구들이 SDK 를 참조해 쓴다
   ctx\
     model.onnx           임베딩 모델 (선택 · 없으면 규칙만)
     index.bin            과거 기록 인덱스
```

- 도구는 `BSP.Contracts` 만 참조하던 규약 그대로, **`IBspContext` 를 주입받는다**
- 런처(프로세스 밖)도 같은 DLL 을 쓴다 — 리빗이 꺼져 있어도 상태를 답한다
- 모델이 없으면 회상만 빠지고 나머지는 그대로 돈다 (지금 만든 규칙판이 그 폴백이다)

## 2-6. 무엇으로 성공을 재나

이 SDK 는 "좋아 보인다" 로 판정하면 안 된다. 1부의 근거가 곧 지표다.

| 지표 | 재는 법 | 목표 |
|---|---|---|
| **되묻는 횟수** | 같은 과제를 스냅샷 있을 때/없을 때 | 30% 감소 |
| **입력 토큰** | 한 과제당 누적 | 1/10 이하 |
| **정확도** | 같은 질문 20개에 대한 정답률 | **떨어지지 않을 것** (조사대로면 오른다) |
| 첫 답까지 시간 | 초 | 절반 |

세 번째가 관문이다. 줄였는데 정답률이 내려가면 압축 규칙이 틀린 것이다.

## 2-7. 단계

| # | 할 일 | 붙는 곳 | 검증 |
|---|---|---|---|
| 1 | `Snapshot()` — 규칙만 (이미 만든 것) | 런처 | 되묻는 횟수 |
| 2 | `Compress()` — 예산·커서·이상치 우선 | 런처 | 8KB 안에 드나 |
| 3 | SDK 로 떼어내기 (`BSP.Context.dll`) | HTS Tools | 도구에서 호출되나 |
| 4 | `Recall()` — 임베딩 인덱스 | HTS · 런처 | 과거 사례가 맞나 |
| 5 | MCP 어댑터 | Bridge | Claude 가 먼저 읽나 |

1·2 는 이미 절반 와 있다. 3부터가 SDK 다.

## 2-8. 안 하는 것

- 생성 모델 학습 — 조사 결과 사실 회상은 검색이 낫다
- 범용 MCP 서버 제작 — 오토데스크 + 오픈소스 다섯이 이미 한다
- 컨텍스트를 키워서 해결 — 1부가 반증한 방향이다
- 자동 판정 결과를 라벨로 재학습 — 품질이 무너진다
