# 지시서 — 배포 서버를 만든다

> 이 파일을 AI(클로드 코드)에게 그대로 주고 시작하면 된다.
> 언어·프레임워크·호스팅은 **만드는 쪽이 정한다.** 아래 «필수» 네 가지만 맞추면
> 현장 PC 의 런처는 아무것도 고치지 않아도 붙는다.

---

## 0. 목표 한 줄

**파일을 올리면, 각 PC 의 리빗이 다음에 켜졌다 꺼질 때 그 파일로 바뀌어 있다.**

사용자는 아무것도 하지 않는다. 설치 프로그램도, 공지도, "받아서 푸세요" 도 없다.

## 1. 런처가 하는 일 (서버가 상대할 것)

```
리빗 켜짐 → GET 카탈로그 → 바뀐 파일만 GET → SHA-256 재계산 → 맞으면 임시 보관
리빗 꺼짐 → 잠금 풀림 → 제자리에 배치 → (선택) 기록 업로드
```

런처는 **상태를 스스로 들고 있다.** 서버가 죽어 있으면 마지막 상태로 계속 돈다.
그러니 서버는 «지금 뭐가 최신인가» 만 정직하게 말하면 된다.

## 2. 필수 — 이 둘만 있으면 배포가 성립한다

### (1) 카탈로그  `GET <아무 주소나>`

주소는 그쪽이 정한다. 런처 `config.json` 의 `manifestUrl` 에 적어 준다.
응답은 이 모양이어야 한다. 필드 이름은 **그대로** 써야 한다.

```json
{ "schema": 2,
  "generated": "2026-09-21T17:00:00",
  "products": [
    { "id": "ceo.tool.demo",
      "name": "표시 이름",
      "publisher": "BSP ENGINEERING",
      "kind": "tool",
      "minRevit": "2024",
      "latest": "3.1.4",
      "versions": [
        { "version": "3.1.4",
          "files": [
            { "path": "demo/sample.dll",
              "size": 25,
              "sha256": "579cea…",
              "url": "http://어디든/blobs/sample.dll" } ] } ] } ] }
```

| 필드 | 규칙 |
|---|---|
| `id` | ASCII 소문자+점. 이 값이 폴더 이름이 된다 |
| `kind` | `platform` (자기 `.addin` 포함) · `bridged` (파일만) · `tool` (관리 폴더) |
| `latest` | `versions` 안에 **반드시 있는** 버전이어야 한다 |
| `path` | 배치될 상대 경로. `..` 금지 |
| `sha256` | 소문자 16진. **틀리면 런처가 배치를 거부한다** (이게 유일한 신뢰 근거다) |
| `url` | 절대주소면 그대로 따라간다. 서명된 CDN 주소·302 리다이렉트 모두 가능 |

**불변식** : 같은 `(id, version, path)` 의 내용은 절대 바뀌지 않는다. 고치려면 새 버전을 낸다.
(런처는 버전이 같으면 받지 않는다. 같은 버전으로 덮으면 현장에 영원히 안 퍼진다.)

### (2) 파일  `GET <위 url>`

바이트 그대로. 인증이 필요하면 런처가 헤더를 하나 붙인다 —
헤더 이름은 `config.json` 의 `authHeader` (기본 `x-bsp-key`), 값은 `token`.

## 3. 선택 — 있으면 좋고 없어도 돈다

| 길 | 쓰임 | 없으면 |
|---|---|---|
| 회원 확인 (`memberUrl`) | 이 회사가 받을 목록 제한 | 카탈로그에 있는 것을 전부 받는다 (서버가 이미 걸러 준 것으로 본다) |
| 기록 수집 (`usageUrl`) | 누가 무엇을 얼마나 썼나 | 기록은 로컬에만 쌓인다 (`runlog.jsonl`) |
| 버그 리포트 | 사용자 신고 | 리포트 기능만 빠진다 |
| 심사·번들·콘솔 | 운영 편의 | 배포에는 영향 없음 |

회원 확인을 쓰려면 응답은 `{"tenant":"…","grade":"…","expires":"…","allow":["id 또는 *"]}`.
`requireMember: true` 로 두면 조회 실패 시 **아무것도 설치하지 않는다**(fail-closed).

## 4. 하면 안 되는 것

- 같은 버전의 파일 내용을 바꾸는 것 (현장에 안 퍼지고, 퍼져도 서로 다른 상태가 된다)
- `sha256` 을 서버가 대충 채우는 것 — 런처는 받은 바이트로 다시 계산해서 대조한다
- 카탈로그를 사용자별로 즉석에서 만들며 `latest` 를 흔드는 것 (되돌리기가 불가능해진다)
- 런처에게 «지금 당장 적용» 을 시키려는 것 — 리빗이 켜져 있으면 DLL 은 잠겨 있다. 설계가 그렇다

## 5. 순서 (이대로 하면 된다)

1. 정적 파일 두 개로 시작한다 — 카탈로그 JSON 하나, 파일 하나. **이 단계에서 이미 배포가 된다**
2. 올리기(업로드) 를 붙인다. 올릴 때 서버가 `sha256` 과 `size` 를 계산해 카탈로그를 다시 쓴다
3. 버전 목록·롤백을 붙인다 (`latest` 를 옛 버전으로 되돌리면 그게 롤백이다)
4. 그 다음에 기록·회원·심사·화면을 붙인다

## 6. 합격 시험 (사람 눈으로 판정하지 않는다)

`AI\selftest.ps1` 을 그쪽 서버 주소로 돌린다.

```powershell
.\AI\selftest.ps1 -ManifestUrl "https://내서버/catalog.json" -Token "…" -AuthHeader "x-bsp-key"
```

통과 기준 — 전부 **자동 판정**된다.

| # | 항목 | 통과 조건 |
|---|---|---|
| 1 | 카탈로그 | 200 · JSON · `products[].latest` 가 `versions` 안에 있다 |
| 2 | 설치 | `bsp-launcher sync` 후 선언한 `path` 에 파일이 있다 |
| 3 | 해시 | 배치된 파일의 SHA-256 이 카탈로그 값과 같다 |
| 4 | 변조 거부 | 해시를 일부러 틀리게 하면 **배치되지 않는다** |
| 5 | 새 버전 | `latest` 를 올리면 옛 파일이 지워지고 새 파일이 놓인다 |
| 6 | 서버 정지 | 서버를 꺼도 런처가 죽지 않고 마지막 상태를 유지한다 |

6개 전부 PASS 가 아니면 완료가 아니다. 부분 통과는 «부분 통과» 라고 적는다.
