# 시험 매뉴얼 — 무엇을 어떻게 확인하는가

> 기준 하나 : **눈으로 봤다고 통과가 아니다.** 아래 시험은 전부 «명령 한 줄» 이나
> «리빗에서 몇 번 누르기» 로 끝나고, 결과가 숫자나 PASS/FAIL 로 남는다.
> 통과하지 못한 항목은 «부분 통과» 라고 적는다. 넘어가지 않는다.

---

## A. 자동 — 명령 한 줄

### A-1. 배포 사슬 `AI\selftest.ps1`

```powershell
.\AI\selftest.ps1                                   # 서버 없이 (로컬 고정물)
.\AI\selftest.ps1 -ManifestUrl https://…/catalog.json -Token …
```

| 항목 | 무엇을 증명하나 | 기대 |
|---|---|---|
| 설치 | 카탈로그가 말한 자리에 놓인다 | PASS |
| 해시 | 받은 바이트가 올린 바이트와 같다 | PASS |
| 변조 거부 | 해시가 어긋나면 **깔지 않는다** | PASS |
| 새 버전 | 옛 파일을 지우고 교체한다 | PASS |
| 서버 정지 | 서버가 죽어도 PC 는 멀쩡하다 | PASS |
| 카탈로그/실제 배포 | (주소를 준 경우) 그쪽 서버로 실제로 깔린다 | PASS |

시험은 **격리된 폴더**에서 돈다(`BSP_STATE_DIR`). 현장 설치 상태를 건드리지 않는다.
현재 기준선 : **5/5 PASS** (서버 미연결 상태)

### A-2. 현재 상태 `AI\healthcheck.ps1`

| 줄 | 정상 |
|---|---|
| 리빗 | 실행 중 / 꺼짐 (둘 다 정상) |
| 매니저 | **돌고 있음 · 1개** — 2개 이상이면 비정상 |
| 심장박동 | 60초 이내 (감시 주기 이내) |
| 제품 | 상태가 `설치됨` 또는 `다음 기동에 적용 N개` |
| Addins 목록 | 전환 뒤에는 **플랫폼 `.addin` 하나**만 남는 것이 목표 |
| 기록 | `기동` 줄의 ms 가 **200 미만** |
| 메모리 | `level` 이 `ok` (warn/high 면 재시작 권고) |

## B. 사람 — 리빗에서 누른다

각 항목은 «어떻게» 와 «통과 조건» 이 짝이다. 통과 조건이 애매하면 그건 시험이 아니다.

### B-1. 엔트리포인트

| # | 어떻게 | 통과 |
|---|---|---|
| 1 | 리빗을 켠다 | **[BSP]** 탭이 있다 |
| 2 | [상태] 를 누른다 | «매니저가 돌고 있습니다» + 경로·버전이 보인다 |
| 3 | 매니저를 강제로 끄고 [상태] 를 다시 누른다 | «꺼져 있습니다» + [지금 띄우기] 가 뜨고, 누르면 다시 산다 |
| 4 | `healthcheck` 의 기록 | `기동 … ok … 200ms 미만` |

### B-2. 프로세스 독립 (이 구조의 핵심)

| # | 어떻게 | 통과 |
|---|---|---|
| 1 | 리빗을 **정상 종료**한다 | 매니저는 계속 돈다 (`healthcheck`) |
| 2 | 리빗을 **작업 관리자로 강제 종료**한다 | 매니저는 계속 돈다 |
| 3 | 리빗을 두 개 켠다 | 매니저는 **여전히 하나** |
| 4 | 로그아웃 → 로그인 | 매니저가 자동으로 다시 떠 있다 |

> 실측 기준선 : 평범한 경우 `detached+breakaway`, 작업 개체(Job) 안이면 `wmi` 로 띄워
> 두 경우 모두 부모가 죽어도 생존. 중복 실행은 즉시 물러남(종료 코드 3).

### B-3. 리빗 안에서 받기

| # | 어떻게 | 통과 |
|---|---|---|
| 1 | 아직 안 깔린 도구를 «받기» | 2~3초 안에 «설치됨» (실측 1.3초) |
| 2 | 이미 쓰고 있는 제품을 «업데이트» | «다음 기동에 적용 N개» 라고 **정확히 말한다** |
| 3 | 리빗을 껐다 켠다 | 그 N개가 실제로 갈려 있다 |
| 4 | 회선을 끊고 «받기» | 리빗이 멈추지 않는다. 실패 문구만 뜬다 |

### B-4. 업데이트 한 바퀴 (전 과정)

1. 도구를 고쳐 버전을 올리고 `publish.ps1` 로 올린다
2. **아무것도 하지 않고** 리빗을 껐다 켠다
3. 통과 : 새 버전이 적용되어 있다 · `healthcheck` 제품 버전이 바뀌어 있다 · 사용자는 아무 조작도 안 했다

### B-5. 사고 기록 (범인 지목)

| # | 어떻게 | 통과 |
|---|---|---|
| 1 | 도구 하나를 실행 중에 리빗을 강제 종료 | 기록에 `crash.attributed` + **그 도구 이름**이 남는다 |
| 2 | 도구를 정상 실행 | `runlog.jsonl` 에 `succeeded` + 소요 ms |
| 3 | 오래 켜 둔다(1시간+) | `memory.json` 이 갱신되고, 단계가 바뀔 때만 기록이 남는다 |

## C. 전환 전후 비교 (숫자로 적는다)

전환 작업의 성과는 이 표로 보고한다. 빈칸을 채워 제출한다.

| 항목 | 전환 전 | 전환 후 | 재는 법 |
|---|---|---|---|
| 리빗 기동 시간 | | | 스톱워치 · 3회 평균 |
| 기동 직후 로드된 애드온 DLL 수 | | | `healthcheck` / 프로세스 탐색기 |
| 리본 탭 수 | | | 눈으로 |
| 업데이트에 드는 사람 손 | 파일 복사 N회 | 0회 | 절차서 |
| «누가 무엇을 썼나» | 알 수 없음 | 기록 N줄 | `healthcheck` |
| 사고 시 범인 특정 | 불가 | `crash.attributed` | 기록 |

## D. 시험 결과 적는 법

```
날짜 / PC / 리빗 버전 / SDK 버전
A-1 selftest        : 5/5 PASS
A-2 healthcheck     : 매니저 1 · 기동 17ms · 메모리 ok
B-1 엔트리포인트     : 4/4
B-2 프로세스 독립    : 4/4
B-3 리빗 안 받기     : 3/4  (4번 회선 차단 시 문구 대신 멈춤 — 미해결)
B-4 업데이트 한 바퀴 : PASS
B-5 사고 기록        : 2/3  (1번 재현 실패 — 재시도 필요)
```

**통과하지 못한 것을 그대로 적는다.** 이 문서의 목적은 합격증이 아니라
«지금 어디까지 믿을 수 있는가» 를 아는 것이다.
