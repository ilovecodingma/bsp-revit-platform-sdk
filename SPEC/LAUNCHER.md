# 런처 최소기능 공통설계

> 이 문서가 런처의 **전부**다. 여기 없는 기능은 런처의 일이 아니다.
> 서버가 무엇이든, 화면이 무엇이든, 애드온이 몇 개든 **이 여섯 가지만** 공통으로 돈다.

---

## 0. 한 문장

**런처는 «리빗 밖에서 도는 작은 상주 프로그램» 이고, 하는 일은 배포 여섯 가지뿐이다.**
정책(누구에게 무엇을 줄지)은 서버가, 화면은 리빗이, 판단은 사람이 한다.

---

## 1. 최소기능 여섯

| # | 기능 | 한 줄 정의 | 실패했을 때 |
|---|---|---|---|
| 1 | **상주** | 한 대에 **하나만** 돈다. 리빗과 수명이 분리된다 | 두 번째는 즉시 물러남(코드 3) |
| 2 | **받기** | 카탈로그를 읽고 **바뀐 파일만** 받는다 | 마지막 상태로 계속 동작 |
| 3 | **검증** | SHA-256 이 맞을 때만 인정한다 | 배치 거부 · 기존 설치 **유지** |
| 4 | **배치** | 잠기지 않은 것은 지금, 잠긴 것은 **리빗 종료 때** | 큐에 남고 다음 종료 때 재시도 |
| 5 | **세션** | 리빗 시작/종료·메모리·모듈·멈춤을 재고 남긴다 | 기록만 빠짐 (업무 무영향) |
| 6 | **요청** | 리빗 안 화면의 «받기» 를 처리한다 | 시간 초과를 화면에 그대로 |

그 외(심사·번들·회원·과금·콘솔)는 **서버의 일**이다. 런처는 모른다.

---

## 2. 불변식 — 이것만 지키면 나머지는 자유

1. **파일은 해시로만 신뢰한다.** 이름·크기·날짜·출처로 믿지 않는다
2. **받고 · 검증하고 · 그 다음에 교체한다.** 순서를 바꾸면 실패했을 때 «아무것도 없는» PC 가 남는다
   *(실측 사고 : 옛 버전을 먼저 지우고 새 버전을 받다 해시가 틀려, 둘 다 없어졌다)*
3. **같은 `(id, version, path)` 의 내용은 영원히 같다.** 고치려면 새 버전
4. **남의 제품 파일은 건드리지 않는다.** 우리가 놓은 것만 우리가 지운다
   *(실측 사고 : 남의 `products.txt` 를 썼다가 도구 33개가 전부 사라졌다)*
5. **업무를 막지 않는다.** 서버가 죽든 기록 전송이 실패하든 리빗은 그대로 돈다

## 3. 밖에서 보이는 면 (이게 공통 규격이다)

### 3-1. 명령

```
bsp-launcher status | sync | watch-revit | log [n] | tail | enable <id> | disable <id>
```

상주로 쓰는 것은 `watch-revit` 하나다. 나머지는 사람이 확인할 때 쓴다.

### 3-2. 설정 — `config.json` (런처 옆)

```json
{ "manifestUrl": "https://어디든/catalog.json",
  "usageUrl":    "",
  "memberUrl":   "",
  "authHeader":  "x-bsp-key",
  "token":       "",
  "revitYear":   "2024",
  "pollSeconds": 60,
  "requireMember": false }
```

- `manifestUrl` 만 있으면 배포가 성립한다. **주소 체계는 서버 쪽 것이다**
- `http(s)` 외에 `file:` 도 된다 → 공유 폴더(`\\파일서버\bsp\catalog.json`)만으로도 배포된다
- 전부 비우면 **오프라인** — 세션 관리(기능 5)만 돈다. 그래도 죽지 않는다
- `BSP_STATE_DIR` · `BSP_ADDINS_DIR` 환경변수로 상태 위치를 옮길 수 있다 (시험·공용 PC)

### 3-3. 파일로 하는 대화 — `%AppData%\BSP\Platform\`

| 파일 | 방향 | 내용 |
|---|---|---|
| `state.json` | 런처 → 화면 | 설치 목록·대기·경고·서버 상태 |
| `agent.json` | 런처 → 누구나 | 심장박동 (pid·시각) |
| `memory.json` | 런처 → 화면 | 메모리·모듈·응답 스냅샷 (**덮어쓰기**) |
| `runlog.jsonl` | 애드온 → 런처 | 실행 기록 한 줄씩 |
| `.running` | 애드온 → 런처 | 지금 도는 도구. 남아 있는데 리빗이 사라지면 **그놈이 범인** |
| `cmd\<티켓>.json` | 화면 → 런처 | 요청 |
| `cmd\<티켓>.done.json` | 런처 → 화면 | 답 |

포트도 서비스도 관리자 권한도 쓰지 않는다. **파일 하나가 프로토콜이다.**

## 4. 리빗 안에서 받기 (기능 6)

대표님이 원하는 «리빗 안에서 목록 보고 눌러서 받기» 는 이 경로로 성립한다.

```
리빗 안 화면        Requests.Install("bsp.hts")
                        │  cmd\<티켓>.json
                        ▼
런처               받기 → SHA-256 검증 → 안 잠긴 것 지금 배치 / 잠긴 것 큐
                        │  cmd\<티켓>.done.json   (실측 왕복 1.3초)
                        ▼
리빗 안 화면        "설치됨" 또는 "다음 기동에 적용 2개"
```

**리빗이 직접 받지 않는 이유**는 하나다 — 리빗이 쥔 DLL 은 리빗 자신도 못 바꾼다
(.NET Framework 에는 어셈블리 언로드가 없다). 그래서 «누르는 것» 은 안에서,
«바꾸는 것» 은 밖에서 한다. 사용자 눈에는 리빗 안에서 다 되는 것으로 보인다.

아직 안 깔린 새 도구는 **지금 바로** 놓이고, 이미 올라가 있는 것만 종료 때 갈린다.
화면은 그 둘을 구분해서 말해야 한다 (`Answer.Pending`).

## 5. 세션 관리 (기능 5) — 밖에서 할 수 있는 만큼만

| 할 수 있는 것 | 못 하는 것 |
|---|---|
| 리빗 시작·종료 감지 | 리빗 안 어셈블리 내리기 |
| 메모리·핸들·스레드·모듈 수 측정 | 강제 GC |
| 응답 없음 판정 + 지속 시간 | 멈춘 도구만 골라 죽이기 |
| `.running` 으로 **범인 지목** | 무한 루프 막기 |
| 세션 요약·누적 기록 | 크래시 자체를 예방 |

그래서 목표를 «막는다» 가 아니라 **«언제 재시작해야 하는지 숫자로 말한다»** 로 잡았다.
기록은 변할 때만 남긴다 — 단계 변화 / 500MB 눈금 / 모듈 25개 눈금 / 세션 종료.

---

## 6. 일부러 넣지 않은 것

| 뺀 것 | 이유 |
|---|---|
| 자동 업데이트(자기 자신) | 런처가 자기를 바꾸면 실패 시 복구 수단이 없다. 배포 대상에서 뺀다 |
| 서비스 등록·관리자 권한 | 설치 장벽이 생기고 보안 심사가 커진다. 로그온 시작으로 충분하다 |
| 강제 종료·프로세스 살해 | 도면이 날아간다. 기록하고 사람에게 알린다 |
| UI | 화면은 리빗 안과 서버 콘솔에 있다. 런처는 화면이 없다 |
| 스케줄러·크론 | 시점은 «리빗 시작/종료» 로 충분하다. 폴링은 세션 감시에만 쓴다 |
