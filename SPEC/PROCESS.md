# 프로세스 구조 — 애드온은 점화만 하고, 관리는 밖에서 돈다

> 관리 기능을 리빗 안에 두면 «리빗이 살아 있는 동안만» 관리된다.
> 그 순간 업데이트·수명·메모리·사고기록이 전부 리빗의 수명에 묶인다.
> 그래서 **프로세스를 하나 더 둔다.**

---

## 1. 두 프로세스

```
        ┌──────────────────── Revit.exe ────────────────────┐
        │  BSP.Platform.Entry.dll  (애드온 · 점화 플러그)     │
        │   OnStartup                                       │
        │     ├ 세션 표시 쓰기   revit\<pid>.json            │
        │     ├ 리본 버튼 1개    [상태]                      │
        │     └ 매니저 점화 ─────────────┐ (백그라운드 스레드) │
        │   OnShutdown : 내 세션 표시만 지움 · 매니저는 안 건드림│
        └───────────────────────────────┼───────────────────┘
                     ▲                  │ CreateProcess
        파일로만 대화 │                  ▼
        %AppData%\BSP\Platform          ┌──── bsp-launcher.exe ────┐
          state.json    (매니저 → 애드온)│  상주 · 하나만 · 화면 없음 │
          agent.json    (심장박동)       │  리빗이 죽어도 산다        │
          runlog.jsonl  (애드온 → 매니저)│  리빗이 없어도 산다        │
          revit\<pid>.json (세션)        └──────────┬───────────────┘
                                                    │ HTTP
                                                    ▼  서버
```

리빗 프로세스는 **서버와 직접 통신하지 않는다.** 회선이 죽어도 도면 작업이 멈추지 않고,
보안 심사에서 «리빗이 밖으로 나가는 통로» 를 따로 설명할 필요가 없다.

---

## 2. «종속되지 않는다» 를 성립시키는 세 가지

애드온이 자식 프로세스를 그냥 띄우면, 그것은 여전히 리빗의 부속품이다.
다음 셋을 **모두** 지켜야 독립이 된다.

| 지켜야 할 것 | 어떻게 | 안 지키면 |
|---|---|---|
| 표준 입출력을 물려주지 않는다 | `DETACHED_PROCESS` | 파이프로 서로 묶여 한쪽이 멈추면 같이 멈춘다 |
| 핸들을 물려주지 않는다 | `bInheritHandles = false` | 리빗이 쥔 파일·포트가 매니저에게 상속된다 |
| 작업 개체(Job)를 탈출한다 | `CREATE_BREAKAWAY_FROM_JOB` | **리빗이 죽을 때 같이 죽는다** |
| 띄운 직후 핸들을 닫는다 | `CloseHandle` ×2 | 리빗이 끝난 프로세스를 계속 붙잡는다 |

### 순서가 곧 안전이다

```
1) detached + breakaway      성공 → 작업 개체 밖이다 (윈도우가 보장)
2) 내가 Job 안인가?  아니오  → 그냥 detached 로 충분
3) Job 안인데 탈출 거부      → 절대 그냥 띄우지 않는다. WMI 로 돌려 띄운다
                               (부모가 WmiPrvSE 가 되어 관계가 끊긴다)
4) 그래도 안 되면 셸          (마지막 수단)
```

> **왜 이 순서인가 — 실측 사고.** kill-on-close 작업 개체 안에서 탈출이 거부됐는데
> «그래도 떴으니 됐다» 며 평범한 detached 로 띄웠더니, 부모가 끝나는 순간 매니저도
> 함께 사라졌다. 로그도 남지 않았다. `IsProcessInJob` 으로 먼저 묻고 WMI 로 우회한다.

리빗이 작업 개체 안에서 도는 경우는 드물지 않다 — 배포 관리 도구, 일부 MDM,
가상화·컨테이너 환경이 그렇다. 한 대에서만 안 되는 현상은 원인을 못 찾는다.

---

## 3. 하나만 돈다

애드온은 리빗이 켜질 때마다 점화를 시도한다. 리빗을 두 개 켜면 두 번이다.
그래서 **매니저 쪽이 자물쇠를 쥔다.**

- 이름 있는 뮤텍스 `Global\BSP.Launcher.Agent.v1` (거부되면 `Local\`)
- 두 번째 인스턴스는 **즉시 물러난다** (종료 코드 3)
- 자물쇠는 프로세스가 죽으면 OS 가 푼다 → 강제 종료·블루스크린 뒤에도 잠기지 않는다
- 애드온은 «자물쇠 → 심장박동(`agent.json`, 4분)» 순으로 확인하고, 살아 있으면 아무것도 안 한다

> 파일만으로 생존을 판단하지 않는다. 파일은 죽은 뒤에도 남는다.

## 4. 누가 언제 무엇을 하는가

| 시점 | 애드온(리빗 안) | 매니저(밖) |
|---|---|---|
| 리빗 기동 | 세션 표시 · 리본 · 점화 | 켜짐 감지 → **받아둔다** (배치는 안 한다) |
| 작업 중 | 실행 기록 한 줄씩 | 60초마다 메모리·모듈·응답 스냅샷 |
| 멈춤 | (아무것도 못 한다) | `.running` + 무응답으로 **범인을 지목** |
| 리빗 종료 | 세션 표시만 삭제 | 잠금 풀림 → **큐 적용** · 기록 업로드 |
| 리빗 없음 | — | 계속 산다. 다음 기동을 기다린다 |

업데이트가 «리빗을 껐다 켜야» 반영되는 것은 제약이 아니라 **설계**다.
.NET Framework 는 어셈블리를 내릴 수 없고, 리빗이 켜져 있는 동안 DLL 은 잠긴다.
그래서 받아두는 일과 갈아끼우는 일을 갈라 놓았다.

---

## 5. 애드온이 커지지 않게 하는 선

애드온에 들어가도 되는 것은 이 셋뿐이다.

1. 세션 표시
2. 점화
3. 상태를 보여 주는 버튼 하나

여기에 업데이트 로직·HTTP·DB·챗을 넣기 시작하면, 처음의 문제로 되돌아간다.
**리빗이 꺼지면 관리도 꺼진다.**

---

## 6. 실측 (2026-09-21)

| 상황 | 방법 | 부모 종료 후 |
|---|---|---|
| 평범한 프로세스 | `detached+breakaway` | **살아 있음** (고아 프로세스) |
| kill-on-close 작업 개체 안 | `wmi` | **살아 있음** (부모 = WmiPrvSE) |
| kill-on-close 안 · 우회 없이 | `detached` | 함께 사망 — 이래서 3번 규칙이 있다 |
| 이미 상주 중 | 점화 안 함 | 중복 없음 (`이미 상주 중`) |
| 두 번째 인스턴스 직접 실행 | 거절 | 종료 코드 3 |

부수로 찾은 것 하나 : 화면 없이 도는 프로세스에서 `Console.OutputEncoding` 을 세우면
예외가 나고 **프로세스가 조용히 즉사**한다. 상주 프로세스는 콘솔이 없을 수 있다는 전제로
써야 하고, 죽은 이유는 `agent.err.log` 에 남긴다.
